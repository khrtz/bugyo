# 作る順番と状態

下の層ができてから上を載せます。どの段階も、`packages/bugyo` のテストに「断られるべきものが断られる」ケースを足してから次へ進みます。

| 段階 | 作るもの | 完了の条件 | 状態 |
| --- | --- | --- | --- |
| 0. 土台 | 構造、lint、依存ルール、feature map、`verify`、プラグイン | 見本アプリで check・test・verify が通り、違反したファイルで各ルールがエラーを出す | 済み |
| 1. 台帳と証拠つきの完了 | `task add` `ready` `start` `show` `done` `rework` `drop` `ls`、`task lint`、種類ごとの証拠 | 見本アプリで、verify が落ちる状態だと `done` が断られ、直すと閉じる。手で `done` に書き換えると `pnpm check` が落ちる | 済み |
| 2. ミスと門番 | `task repro`、`mistake`、`gate` | 同じ種類の手直しを2回記録すると門番が不合格になり、ルール化を記録すると戻る | 済み |
| 3. エージェントへの組み込み | スキルの書き換え、フック、CI でのタスク必須化 | スキルが呼ばれなくても、証拠なしでは完了にならない。偽の証拠ファイルを置くと CI が落ちる | 一部（CI での証拠の取り直しと設定の変更の検出は済み。スキルの書き換え、フック、タスクに紐づかない PR の検出は未着手） |
| 4. 作業セッション | `bugyo run <id>`、worktree、着手の印 | タスクを1件任せると、worktree で作業し、証拠つきで閉じて PR が開く | 未着手 |
| 5. 常駐エージェント | エージェント定義、巡回、ルール、inbox。まず番人1体 | わざと壊した機能を番人が次の巡回で見つけ、再現テストつきのタスクを作り、人に聞いてから修正を任せ、証拠つきの PR を持ってくる | 未着手 |
| 6. 並列と自動マージ | 残りの役、複数の作業セッション、最後に自動マージ | 機能が重ならない3タスクを同時に走らせ、3つとも証拠つきで閉じる。門番が不合格のときは動かない | 未着手 |

設計は [tasks.md](tasks.md)（段階1〜3）と [agents.md](agents.md)（段階4〜6）にあります。

## 決まっていないこと

- **巡回を定期的に起動する方法。** OS のスケジューラ、Claude Code のスケジュール機能、CI の定期実行のどれかです。段階5で試して決めます
- **門番のしきい値。** 20件中2件、16件という数字は仮で、運用しながら決め直します（`.bugyo/config.json` の `gate` で変えられます）
- **タスクの親子関係。** 持ち方が決まっていないので、`bugyo task tree` はまだありません
- **`ready` の優先度。** 今は作った順に出します。優先度の項目を持つかは、実際に使ってから決めます
- **Claude Code のフックの使い方。** 段階3で仕様を確かめてから決めます
- **見た目の変更の判定。** スクリーンショットの差分が意図どおりかは機械だけでは決められません。基準画像を更新したタスクは人の確認を必須にする案です

## 確かめていないこと

- プラグインのうち、`bugyo-mode`、`bugyo-critique`、`slop-reviewer` は実際の作業で試していません
- `node-lib` のテンプレートは、テストとリポジトリの外での通し確認（`pack` → `init` → `install` → check・test・verify、`new feature` のあとも同じ）だけで、実際の開発に使ったことはありません
- タスク台帳と門番は、テストと見本アプリでの手の確認だけで、エージェントに実際の仕事を任せて回したことはありません
- 門番が「合格 → 不合格 → 合格」と動くことは、しきい値を小さくした設定でだけ確かめています。既定の20件で回したことはありません
