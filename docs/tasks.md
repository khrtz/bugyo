# タスク台帳と門番（設計）

状態: 設計のみ・未実装。このページのコマンド（`bugyo task`、`bugyo mistake`、`bugyo gate`）はまだありません。

エージェントに任せる仕事を1件1ファイルで残し、証拠が通ったときだけ閉じられるようにする層です。完了かどうかを決めるのはエージェントの報告ではなく、台帳の判定です。

## タスクの形

タスクは `.bugyo/tasks/<id>.md` に1件1ファイルで置きます。複数のエージェントが同時に別のタスクを更新しても衝突せず、人もエディタでそのまま読めます。

```md
---
status: active
type: bugfix
feature: todos
blocked-by:
assignee: worker-1
rework: 0
gate-attempts: 1
---

# 絞り込みを切り替えると残り件数がずれる

（何が起きているか、どうなれば終わりか）
```

frontmatter は `key: value` の1段だけにします。feature map と同じ読み込み方で済みます。

| 項目 | 意味 |
| --- | --- |
| `status` | `open`（未着手）→ `active`（作業中）→ `done`（証拠つきで完了）。やめたものは `dropped` |
| `type` | 変更の種類。完了に必要な証拠がこれで決まる |
| `feature` | `docs/features/<id>.md` の `id`。どの機能を verify するかがこれで決まる |
| `blocked-by` | 先に終わっている必要があるタスクの id（カンマ区切り） |
| `assignee` | 作業中のエージェント名か人の名前 |
| `rework` | 完了後に人が手直しした回数 |
| `gate-attempts` | 完了を試みた回数 |
| `evidence-*` | 完了時に CLI だけが書く。check の結果、verify の結果ファイル、そのときのコードのハッシュ |

完了したタスクは `.bugyo/tasks/archive/` に移します。一覧もエージェントが読む量も増え続けません。

## コマンド

エージェントが使うのは `ready` → `start` → `show` → `done` の4つです。出力は1タスク1行で、`--json` を付けると短い JSON になります。

| コマンド | 使う人 | すること |
| --- | --- | --- |
| `bugyo task add "<タイトル>" --type <種類> --feature <id>` | 人・エージェント | タスクを作る。`--feature` が feature map になければ断る |
| `bugyo task ready` | エージェント | 未着手で、ブロックされていないタスクを優先度順に出す |
| `bugyo task start <id> --as <名前>` | エージェント | 作業中にする。すでに誰かが作業中なら断る |
| `bugyo task show <id>` | エージェント | 本文、読むべき feature map、完了に必要な証拠を出す |
| `bugyo task repro <id> -- <テストコマンド>` | エージェント | バグ修正用。直す前にテストが失敗することを記録する |
| `bugyo task done <id>` | エージェント | 証拠を取り、通れば閉じる。通らなければ理由を出して作業中のままにする |
| `bugyo task rework <id> -r "<理由>" --kind <ミスの種類>` | 人 | 完了したタスクを作業中に戻し、手直しとミスの種類を記録する |
| `bugyo task drop <id> -r "<理由>"` | 人 | やめる |
| `bugyo task ls` / `tree` | 人 | 一覧と親子関係 |
| `bugyo task lint` | `pnpm check`・CI | 台帳の整合を検査する |
| `bugyo mistake ls` / `rule <種類> --at <パス>` | 人・エージェント | ミスの一覧と、ルール化したことの記録 |
| `bugyo gate` | 人・CI | 任せる範囲を広げてよいかを計算する |

`show` は、エージェントがこれだけで「どこを読み、何を出せば終わりか」が分かる出力にします。

```
t-014 [active/bugfix] 絞り込みを切り替えると残り件数がずれる
読む: docs/features/todos.md
完了に必要: repro の記録 → 同じテストが通る → pnpm check → pnpm test
```

## 証拠つきの完了

タスクを `done` にできるのは `bugyo task done <id>` だけで、このコマンドが自分で証拠を取ります。エージェントの「確かめました」という報告は使いません。

1. タスクの `type` から、必要な証拠を決める（下の表）
2. `pnpm check` → `pnpm test` → 必要なら `bugyo verify <feature>` を順に実行する
3. すべて通れば、結果の要約を `.bugyo/evidence/<id>.json` に書き、`evidence-*` を埋めて `done` にする
4. どれかが落ちたら、落ちたコマンドと末尾30行だけを出し、`gate-attempts` を1増やして `active` のままにする

| `type` | 変更の種類 | 完了に必要なもの |
| --- | --- | --- |
| `feature` | 新しい機能 | check、test、verify。feature map の4見出しが雛形のままでないこと |
| `ui-flow` | UI の操作 | check、test、verify |
| `ui-look` | UI の見た目 | check、verify。基準画像を更新した場合は、そのことをタスクに記録する |
| `logic` | `model/` のロジック | check、test。その機能の `model/` にテストがあること |
| `bugfix` | バグ修正 | `repro` の記録（直す前に失敗したテスト）と、同じテストが今は通ること。check、test |
| `refactor` | リファクタリング | check、test。テストファイルを変えていないこと（`start` 時に記録したハッシュと比べる） |
| `chore` | 設定・文書 | check のみ |

証拠が古くなったことも分かるようにします。`evidence-tree` に、証拠を取ったときの `src/` と `e2e/` の内容のハッシュを入れます。CI は、その PR で閉じたタスクについてだけ、ハッシュが今のコードと合うかを確かめ、合わなければ証拠を取り直します。過去に閉じたタスクは照合しません（後の変更で必ず合わなくなるためです）。

動画やトレースは git に入れません。リポジトリに残すのは要約の JSON（どの spec が通ったか、結果ファイルの場所、ハッシュ）だけで、実物は手元の `artifacts/` と CI の成果物に置きます。

## 機械的に守らせる場所

必ず守らせたいことは、スキル（文章の指示）ではなく CLI・`pnpm check`・CI で止めます。スキルは呼ばれないことがある、という前提で作ります。

| どこで止めるか | 止めるもの |
| --- | --- |
| CLI | `done` だけが証拠を取って書く。`start` は二重着手を断る。`add` は feature map にない機能を断る |
| `bugyo task lint`（`pnpm check` に入れる） | 手で `status: done` に書き換えたタスク（証拠ファイルがない）、担当のいない `active`、1人が2件同時に `active`、存在しない `blocked-by` |
| CI | タスクに紐づかない PR（ブランチ名 `task/<id>` で判定）、`evidence-tree` が今のコードと合わないタスク。その PR で閉じたタスクの証拠は取り直して比べる |
| Claude Code のフック | セッション開始時に `bugyo task ready` を見せる。`active` なタスクを残したまま終わろうとしたら知らせる |

台帳も証拠もただのファイルなので、手で書き換えること自体は防げません。手元の `task lint` で分かるのは「証拠ファイルのない完了」までです。偽の証拠ファイルまで止めるのは CI で、証拠を取り直して比べます。フックは思い出させる役で、止める役は上の3つが持ちます。

## ミスの記録とルールへの昇格

ミスは種類ごとに `.bugyo/mistakes/<種類>.md` へ1ファイルで残し、同じ種類が2回起きたら、ルールに変えるまで門番を不合格にします。

1. 人が手直しするときに `bugyo task rework <id> --kind <種類>` を実行する。既存の種類の一覧が出るので、近いものがあればそれを選ぶ
2. ミスのファイルに、起きたタスクの id と回数が追記される
3. 同じ種類が2回目になると、`bugyo task lint` が警告し、`bugyo gate` が不合格になる
4. ルールに変える。優先する順は、型・API → lint・依存ルール → テスト・feature map → `CLAUDE.md`
5. `bugyo mistake rule <種類> --at <ルールを書いたファイル>` で記録する。そのファイルが実在しなければ断る
6. ルール化済みの種類がまた起きたら、「ルールが漏れている」として最優先で表示する

## 門番（`bugyo gate`）

エージェントに任せる範囲を広げてよいかを、直近20件の完了タスクから計算します。3つの条件をすべて満たしたときだけ合格です。

| 条件 | 計算 | 最初のしきい値（仮） |
| --- | --- | --- |
| 人の手直しがほとんど要らない | `rework` が1以上のタスクの件数 | 20件中2件以下 |
| check と verify が1回で通っている | `gate-attempts` が1回で閉じたタスクの件数 | 20件中16件以上 |
| 同じ種類のミスが再発していない | 2回以上起きて、まだルール化されていない種類の数 | 0 |

しきい値は `.bugyo/config` で変えられます。完了タスクが20件に満たない間は「件数不足」で不合格です。複数の作業セッションの同時実行と自動マージ（[agents.md](agents.md)）は、この判定が合格でないと動きません。土台が回る前に任せる範囲を広げると、質の低いコードが速く増えるだけだからです。
